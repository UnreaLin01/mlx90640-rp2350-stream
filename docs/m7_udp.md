# M7 乙太網路串流量測紀錄

日期：2026-09-20　韌體：`mlx_thermal_udp`（UDP）／`mlx_thermal`（USB，對照）

## 1. 換傳輸層改了什麼

`main.c`、`protocol.c`、`stream.c`、感測器程式**完全沒有改動**。只新增：

- 韌體：`src/transport_udp.c`（實作 `transport.h`）＋ 建置目標 `mlx_thermal_udp`（連結 `stream_udp` 而非 `stream_usb`）。
- 電腦端：`mlxstream/udp_source.py`（新的資料來源）＋ `sources.open_source()`；所有工具改用 `--source usb|udp`。解析、統計、溫度換算、顯示的程式碼未改。
- 協定新增 type 4 REQUEST（電腦 → 開發板），見 `docs/protocol.md`。

REQUEST 機制：電腦每秒送一次，開發板據此學到回送位址、並在 3 秒內沒收到就停止傳送。解決三件事：電腦 IP 由 DHCP 變動、Windows 防火牆預設擋下未經請求的輸入封包、規格要求 EEPROM 可「回應請求」。

## 2. 驗收結果

### 掉包率與幀率

|---|---|---|---|
| subpage 數 | 9,391 | 3,755 | 3,756 |
| CRC 錯誤／序號跳號／不完整 | 0／0／0 | 0／0／0 | 0／0／0 |
| **掉包率** | **0%** | **0%** | 0% |
| 裝置端速率 | 31.299 Hz | 31.281 Hz | 31.296 Hz |
| 電腦端接收速率 | 31.301 Hz | 31.288 Hz | 31.294 Hz |

| EEPROM 重送 | 151 次，全部相同 | 61 次 | 60 次 |

驗收要求「連續 60 秒掉包率 < 0.1%」：300 秒 0 掉包，通過。幀率與 M3 量得的 31.28 Hz 相符（誤差 < 0.1%）。

### 延遲與穩定度比較（裝置時間戳 vs 電腦收到時間，取相對最快封包的分布）

| | USB | UDP（乙太網路 → 路由器 → Wi-Fi） |
|---|---|---|
| 中位數 | 3.01 ms | 3.68 ms |
| 99% | 5.84 ms | 59.0 ms |
| 最大 | **8.83 ms** | **129.3 ms** |

兩者中位數接近，但尾端差很多：USB 抖動上限不到 9 ms，UDP 偶爾出現數十至上百毫秒。差異來自路徑中的 Wi-Fi 段（電腦沒有實體網路埠），不是開發板或 W6300。資料沒有遺失，只是到達時間不均；即時顯示看得出偶爾停頓，對呼吸率（0.1～1 Hz）分析無影響，因為每個 subpage 都帶有裝置端時間戳。

### 顯示程式不需修改

`host/viewer.py --source udp`：31.29 Hz、0 錯誤，影像與溫度正常（`docs/m5_display.md` 的程式未改一行）。

## 3. 連線瞬間的 ARP 停頓（已知現象）

第一次測試時，在電腦剛連上的瞬間出現 1 次 subpage 漏讀（間隔 78 ms，正常 32 ms），之後 2,000 多個 subpage 全部正常。

原因：開發板第一次送封包給該電腦時，必須先用 ARP 取得對方 MAC，WIZnet 的 `sendto` 會等回應；經 Wi-Fi 這次等了約 78 ms，讀取迴圈被卡住，漏掉 2 個 subpage 週期。

後續測試（300 秒、120 秒）皆未再出現：板子的 ARP 快取已有對方位址。屬一次性、可解釋的現象。

- 影響：連線瞬間可能漏 1～2 個 subpage。
- 若要完全避免：把網路處理移到第二顆核心（CLAUDE.md 架構原則已預留「雙核分工」），感測器讀取就不會被任何網路等待卡住。之後若要加 mDNS／NetBIOS 之類需要持續回應查詢的服務，建議一併處理。
- `host/stream_stats.py` 會把連線後 2 秒內與之後的交替錯誤分開計算。

## 4. M7 結論

依 CLAUDE.md 的 M7 驗收條件全部通過：連續 60 秒（實測 300 秒）掉包率 0%、幀率符合 M3 設定、M5 顯示程式不需修改即可運作、USB 與乙太網路的延遲與穩定度比較已記錄。
