# M3 讀取時序量測紀錄

日期：2026-09-20　韌體：`mlx_thermal`（32 Hz）、`mlx_thermal_64hz`
硬體限制：I2C 上升時間約 220 ns（見 `docs/m2_i2c.md`）

## 1. 做了什麼

| 改動 | 效果（整份 EEPROM／subpage 讀取） |
|---|---|
| M2 基準：SDK 逐位元組讀取，lcnt 90／hcnt 60 | 20.07 ms（EEPROM） |
| DMA 讀取（兩個 DMA 通道餵 I2C FIFO，位元組間無空檔） | 18.77 ms（EEPROM），線上 0 差異 |
| SCL 時序 lcnt 77／hcnt 57 | 17.48 ms（subpage） |

- DMA 通道用 `dma_claim_unused_channel()` 動態取得，不佔用 PIO，不寫死通道編號（W6300 驅動可自行取得資源）。
- I2C 設定 RX FIFO 滿時暫停匯流排（`RX_FIFO_FULL_HLD_CTRL`），DMA 來不及搬時不會丟資料。
- subpage 讀取直接呼叫 Melexis `MLX90640_GetFrameData`：確認 new-data 旗標 → 寫 0x0030 清旗標 → 讀 768 像素 → 讀 64 aux → 讀控制暫存器 → 資料檢查。韌體先以 200 µs 間隔輪詢 status，偵測到新資料才呼叫它。

## 2. 32 Hz 量測（Logic 8，50 MS/s，2 秒）

標記：mark A（GP6）＝讀取中；mark B（GP7）＝每個新 subpage 翻轉一次。
工具：`python host/tools/check_m3_timing.py captures/m3_32hz/digital.csv`

| 項目 | 結果 |
|---|---|
| 讀取時間（mark A） | 中位數 17.484 ms（17.482～17.486） |
| subpage 週期（mark B） | 中位數 31.974 ms（31.707～32.004）→ 實際約 31.3 Hz（感測器內部振盪器） |
| 讀取時間／週期 | **55.1%**（目標 < 50%）❌ |
| subpage 編號交替 | 全部 0／1 交替，無遺漏 |
| SCL 實際速率 | 893 kHz（原 806 kHz） |

SCL 時序（以 τ=260 ns 由 Logic 8 門檻換算到 I2C 量測點）。高／低電位用 100 MS/s 另外擷取一次 subpage 讀取（15,255 個 bit，`captures/m3_scl_100m/`），因為 50 MS/s 的 20 ns 取樣間隔會讓最小值看起來偏小：

| 項目 | Logic 8 門檻處（100 MS/s） | 換算到規格量測點 | I2C 1 MHz 規格 | 專案規則 |
|---|---|---|---|---|
| tLOW（30%～30%） | 610～630 ns | 最短 608 ns，平均 623 ns | ≥ 500 ns ✅ | ≥ 600 ns ✅ |
| tHIGH（70%～70%） | 500～520 ns | 最短 280 ns，平均 289 ns | ≥ 260 ns ✅ | — |
| SDA setup（SDA 70% → SCL 30%） | 最小 360 ns（22 萬個 bit，50 MS/s） | 約 140 ns | ≥ 50 ns ✅ | — |

為什麼 tHIGH 不能再縮：上升慢，SCL 在 Logic 8 門檻後約 220 ns 才到 70% VDD，所以 Logic 8 看到的 500 ns 高電位，真正符合規格定義的只有約 282 ns。

## 3. 64 Hz（挑戰目標）

subpage 週期約 17.55 ms，讀取需 17.48 ms，**讀取時間幾乎等於整個週期**：
- 每秒只收到約 56 個 subpage（應為 57）
- subpage 順序錯誤每秒 5～7 次（漏掉 subpage）
- Melexis 資料檢查錯誤（-8，讀到正在更新的資料）每秒約 1～2 次

結論：在目前 I2C 硬體下 64 Hz 不可行。

## 4. 為什麼到不了 50%

一個 subpage 的讀取約 15,600 個 bit 時間（像素 1536 bytes + aux 128 bytes + 位址、status、控制暫存器）。
32 Hz 要 < 50%，需要 < 15.85 ms（最短週期 31.71 ms 的一半）→ 每個 bit ≤ 1.015 µs。

| 做法 | 每 bit | subpage 讀取 | 問題 |
|---|---|---|---|
| 目前 | 1.12 µs | 17.48 ms（55%） | — |
| 理想 1 MHz（上升夠快時） | 1.00 µs | 約 15.6 ms（49%） | 需要改善上拉（硬體） |
| 在目前硬體硬縮 lcnt | 1.015 µs | 約 15.85 ms（50%） | setup 餘裕剩約 55 ns（規格 50 ns，幾乎沒有安全空間），tLOW 約 515 ns 違反專案規則 |

## 5. 決定與結論

使用者 2026-09-20 選擇選項 1：**維持 32 Hz**，M3 驗收改為「讀取在下一個 subpage 就緒前完成且留有餘裕，10 分鐘無遺漏、無錯誤」。M3 通過（55%，餘裕約 14 ms；19,009 個 subpage 0 錯誤）。
64 Hz 列為已知問題（見 CLAUDE.md「已知問題」）。

### 當時列出的選項

1. **接受 32 Hz、55%**：讀取仍在下一個 subpage 前約 14 ms 完成，10 分鐘 19,009 個 subpage 0 錯誤。把 M3 驗收改為「讀取時間 < 週期且留有餘裕，長時間 0 錯誤」。
2. **改用 16 Hz**：實測 27.4%，完全符合原本的驗收條件；對之後的呼吸率量測也足夠（且雜訊較低）。
3. **改硬體（加強上拉）後再回來做 M3**：預估可接近 49%，仍然很邊緣。
4. **只讀需要的那一半資料**：需改用 interleaved 模式（逐列交替），每個 subpage 只讀 12 列 + aux，讀取時間約減半，32 Hz 約 28%，64 Hz 也可能可行。代價：偏離 Melexis 的預設 chess 模式與 `GetFrameData` 讀法，影像品質／校正需要另外評估。
