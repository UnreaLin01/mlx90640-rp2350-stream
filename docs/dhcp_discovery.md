# DHCP 與自動找到開發板

日期：2026-09-20　韌體：`mlx_thermal_udp`、`net_test`

## 1. 開發板取得位址

`src/net.c`：開機先試 DHCP，逾時就用固定位址。整段等待都在核心 1，核心 0 照常讀感測器（log 可見 DHCP 進行中仍持續輸出 32 subpages/s）。

```c
struct net_config {
	bool use_dhcp;
	uint32_t dhcp_timeout_ms;
	uint8_t ip[4], mask[4], gateway[4];   /* DHCP 失敗時使用 */
};
```

目前設定：DHCP 開啟、逾時 15 秒、備援位址 192.168.1.200。拿到租約後 `net_poll()` 在核心 1 的迴圈中持續續約。

### 兩個踩到的點

1. **連上網路線後要等一下再送 DHCP**：交換器的埠剛連上時還不轉送封包，太早送出的 DISCOVER 會石沉大海。WIZnet 自己的範例也等 2 秒，我們用 `LINK_SETTLE_MS = 2000`。
2. **逾時要涵蓋函式庫的重試**：ioLibrary 的 `DHCP_WAIT_TIME` 是 10 秒。原本逾時設 5 秒，第一個 DISCOVER 掉了就直接放棄，看起來像「DHCP 完全不能用」。改成 15 秒後一次成功。

診斷方式：在 `run_dhcp()` 內記錄狀態變化與 DHCP socket 收到的位元組數，`rx seen 0` 代表沒有任何回應（送不出去或對方沒回），`rx seen 313` 代表收到 OFFER／ACK。

## 2. 電腦端自動找到開發板

`host/mlxstream/udp_source.py`：

1. 先試**上次記住的位址**（`host/.board_address`，不進 git）或命令列指定的位址，用單播 REQUEST。
2. 沒有回應時，同時往**廣播位址**送 REQUEST，每 0.25 秒一次，直到板子回應。
3. 板子的回應是單播，來源位址就是它的真實位址。之後所有 REQUEST 只送往該位址（每秒一次保活），並把位址存起來。

### 為什麼廣播只用來搜尋

Wi-Fi 的廣播與多播訊框**不會被 ACK、也不會重傳**（802.11 的規則），AP 還會為了省電模式緩衝它們，所以丟失率明顯高於單播。因此：

- 廣播只出現在「還沒找到板子」的階段，而且會持續重試，掉幾個不影響結果。
- 找到之後全部改用單播，串流本身完全不依賴廣播。
- 有快取位址時，通常連一個廣播封包都不需要送。

## 4. 排錯筆記：RTT 的殘留資料

RTT 上傳緩衝區有 8 KB。logger 附著時會先讀到**上一次執行留下的舊內容**（約 15 秒份），接著才是新資料，因此 log 開頭常出現「看似多了一次開機」。實際以「只重置不燒錄」測試 60 秒，只有一次開機。分析 log 時要注意這點。
